# Ankiデータ交換の契約

更新日：2026-10-14。現行JSONの往復を最初の実装対象にする。完全なコレクション復元と、ノート内容のコピーを区別する。

## 互換性の段階

| 段階                    | 対象                                         | 保持する内容                                           | 前提・限界                                                       |
| ----------------------- | -------------------------------------------- | ------------------------------------------------------ | ---------------------------------------------------------------- |
| 作成用JSON/CSV/Markdown | `front`/`back`中心の入力                     | 作成する質問・回答・指定タグ                           | 改行変換や取り込みタグがある。バックアップ形式ではない           |
| ノート内容JSON          | CLIの `export --format json` → `note import` | 任意のフィールド名・値、モデル名、タグ、送信先デッキ名 | 接続先に同じフィールド構成のモデルが必要。新しいノートとして作成 |
| 版付き交換アーカイブ    | 次の設計・実装対象                           | モデル定義、各カードの所属、メディア実体と参照、出所   | 能力確認、整合性、復元計画が必要                                 |
| 復習状態までの復元      | 後続の検証対象                               | 予定、記憶状態、復習履歴、設定                         | API・形式・版の互換性を確認。ノート内容JSONでは保証しない        |

現在のJSONは、Anki自身が直接読む標準JSON形式ではない。Ankinikiのimport経路を通してAnkiConnectへ渡す。

記事の読者向けに配る教材は、元のコレクションを復元する交換とは別に扱う。[教材・学習体験の設計](content-and-learning.md)では、同じソースから静的Webの練習と、モデル・必要なメディアを含むAPKGを作る方針。専用モデルでの[`content export`](../reference/content-apkg.md)は実装済みで、Webの練習は後続。公開配布物に個人の履歴・設定を含めず、安定した教材identityと更新時の検証を用意する。任意のAnkiモデルやコレクション全体を復元する形式は引き続き未実装。

## 現行のノート内容JSON

CLI exportの配列をそのまま受け取れるようにする。

```json
[
  {
    "noteId": 1700000000000,
    "deckName": "Programming::Rust",
    "modelName": "Code Example",
    "tags": ["rust", "borrowing"],
    "fields": {
      "Question": "<p>Explain this example.</p>",
      "Code": "<pre>let value = 1;\nprintln!(\"{}\", value);</pre>",
      "Explanation": "",
      "Source": "notes/example.md"
    }
  }
]
```

保持するもの：

- フィールド名とフィールド値。値はAnki側のHTMLを含む文字列として扱う。
- 空文字、前後の空白、改行、Unicode、Clozeの記法。
- モデル名とタグ。明示的に指定された追加タグだけを加える。
- 既定のコピー先デッキ名。明示的な `--deck-name` はコピー先の変更を表す。

交換経路では `trim`、改行から `<br>` への変換、独自取り込みタグの追加を行わない。表示用のプレビューと保存値を分離する。

`noteId` は出所の参照。初期importは新しいノートの作成であり、元のIDを指定したupdate/upsertにはしない。同じコレクションへの再importはAnki側で重複として拒否される可能性がある。再実行を安全なupdateに変えるには別のidentity・差分契約が必要。

モデルは名前だけで互換と見なさず、接続先のフィールド名を確認する。フィールドの不足・余分・未対応モデルを黙って省略しない。確認ができなければ、そのノートの書き込みを行わない。

CLIのノート検索は子デッキも含み得る。ひとつのノートから複数のカードが生成され、異なるデッキに所属する場合もある。現行JSONの `deckName` はコピー先を表し、元のカードごとの所属を復元する情報ではない。

JSONはメディア参照を含むHTMLを保つが、画像・音声ファイルを同梱しない。テンプレートやCSSも含まない。対象のモデルやメディアを別途揃える必要がある。完全な復元が必要な間は、Ankiのネイティブexport/importを利用する。

## 入力とエラー

- `fields` は一つ以上の、空でない名前と文字列値の組。空値のフィールドは許可する。
- モデル名、デッキ名、タグの型を検証する。Ankiの名称やHTMLを独自の都合で正規化しない。
- 配列中の作成用レコードと交換用レコードは判別して扱う。
- preview/dry-runは書き込みを行わない。構造検証と接続先の互換性確認を区別して表示する。
- importはノートごとの成功・失敗を返す。全体が成功したと偽らず、通信エラーも結果に含める。
- 更新・削除モードを追加するときは、変更計画と適用条件を独立した契約として設計する。
- 現行の交換用レコードで未定義のトップレベル項目はエラーにする。予定などを追加しても、黙って省略してimportしない。
- `bundle` は作成用のFront/Back入力を対象とする。交換用レコードはモデルやフィールドを落とさないため拒否する。

## 版付きアーカイブの案

JSONの配列形式は既存互換のため維持する。より広い情報を扱う際は、`format` と `formatVersion` を持つ別の包みを導入する。未対応の版を推測して読み込まない。

アーカイブの構成候補：

- `manifest.json`：形式、版、作成日時、作成元・対象範囲、能力情報、保証範囲。
- `models.json`：フィールド順、テンプレート、CSS、モデルの識別・整合性情報。
- `notes.json`：ノート内容、タグ、元のID、提供される場合のGUID。
- `cards.json`：ノートとの関係、テンプレート識別、カード別のデッキ所属。
- `media/` と索引：論理名、形式、サイズ、内容ハッシュ、バイト列。
- 任意の予定・履歴ファイル：読み書きの能力と版が確認できる場合だけ含める。

未知の拡張データを読み書きで捨てない。復元時に解釈できない項目は保持できることと適用できることを区別する。ファイル自体の往復テストと、Ankiへの復元テストも分ける。

書き出し中にAnkiが編集・復習されれば、複数APIの結果が別の時点を表すことがある。整合したsnapshotの能力がない接続先で完全な整合性を宣言しない。

## 接続先に求める能力

- デッキ、ノート、モデル、カード別所属の読み取り。
- フィールドの完全な保存とモデル整合性の確認。
- メディアの取得・保存とハッシュ検証。
- モデル作成・照合、テンプレートとCSSの保存。
- 整合したsnapshotとバッチ処理の上限。
- 予定・履歴の読み書き、対応形式の版と適用条件。

adapterは実際に提供する能力だけを報告する。既存AnkiConnectで不足する機能は、ネイティブpackageによる交換か将来のconnectorで補うことを検討する。機能不足が未確認の段階ではconnector全体を先に作らない。

## 検証fixture

Basic、Cloze、独自フィールド、日本語モデル名、空値、前後空白、複数行コード、HTML、Unicode、画像・音声参照、タグなしを含める。

元データと再解析した保存値を比較し、Anki書き込みのmockに渡されたフィールドとタグも確認する。モデルの欠落・フィールド不一致・通信失敗・混在レコード・dry-runを検証する。

実際のAnkiへ書き込む試験は、専用テストコレクションとbackupを使い、通常の自動テストから切り離す。データを渡せるだけで復習状態も互換と結論しない。
